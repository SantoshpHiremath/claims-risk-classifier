# claims-risk-classifier

A real, genuinely-trained classical machine learning project: a
scikit-learn `RandomForestClassifier` predicting whether an insurance
claim should be flagged as high-risk, with a proper train/validation/
test split, multiple evaluation metrics appropriate for an imbalanced
task, decision-threshold tuning, and an honestly-reported, imperfect
result — not a cherry-picked or inflated one.

Built to close a specific, named gap: classical machine learning that
is "coursework only, not yet project-backed" (as an existing cover
letter for Exxeta's Werkstudent AI & LLM Engineering posting already
disclosed directly, rather than overselling it). This project is that
gap, closed with real, tested code.

## What this is (and isn't)

- **The dataset is synthetic**, generated by `src/generate_data.py` — a
  claims-shaped table (claim type, amount, days since policy start,
  days to report, prior claims, customer age) with a `high_risk` label
  driven by a real, hand-designed underlying rule (unusually high claim
  amount relative to the claim type's norm, claims reported very soon
  after an incident, several recent prior claims, or a very new policy)
  plus ~8% injected label noise. **It is not real insurance data, and
  the risk rule is not a claim about how real insurers detect fraud** —
  it exists to create a genuinely learnable but non-trivial supervised
  classification task.
- **The label is intentionally imbalanced** (~9% positive), mirroring
  real fraud/risk-flagging tasks, where accuracy alone is a misleading
  metric — a classifier that always predicts "not high risk" scores
  ~91% accuracy while catching zero real cases. This project reports
  precision, recall, F1, and ROC-AUC, not just accuracy, specifically
  because of that trap (demonstrated directly below).
- **The model is a real, fitted `RandomForestClassifier`** — not a
  mock, not a lookup table. Training, evaluation, and inference on new
  data all run real scikit-learn code.
- **Honest scope**: this shows the actual skill — correctly splitting
  data (with a validation split kept separate from the test set for
  threshold tuning, so the test metrics are not leaked-into), encoding
  features consistently between training and inference, choosing
  metrics appropriate to an imbalanced problem, and reporting a real,
  imperfect result rather than a suspiciously perfect one. It is not a
  claim about what any model would achieve on real insurance data,
  whose true risk drivers and label noise are unknown to me.

## The result, honestly

```
Tuned decision threshold: 0.39 (chosen on a validation split by F1)
Test set: 750 claims, 68 genuinely high_risk (9.1%)

--- At the tuned threshold ---
Accuracy:  0.8107
Precision: 0.1864
Recall:    0.3235
F1:        0.2366
ROC-AUC:   0.6247  (threshold-independent)

--- Compare: at the naive default 0.5 threshold ---
Accuracy: 0.9080  (looks better...)
F1:       0.1039  (...but this is worse: mostly predicting the majority class)
```

ROC-AUC of ~0.62 is the honest headline number: real, above-chance
signal (0.5 would be random guessing), on a genuinely hard, imbalanced
task — not evidence of a production-ready fraud detector. The
comparison against the naive default threshold is the actual point of
this project's "here's what I learned" story (see Bugs found below):
accuracy alone looked *better* at the default threshold while recall
was almost entirely broken, which is exactly the trap that makes
metric selection matter on imbalanced classification tasks.

## Bugs found and fixed during development

Documented honestly, matching the discipline used elsewhere in this
portfolio:

1. **The default 0.5 decision threshold was badly miscalibrated.** The
   first version trained the model with `class_weight="balanced"` and
   evaluated at the standard 0.5 probability threshold, which gave a
   deceptively good-looking 90.8% accuracy but only 5.9% recall — the
   model was essentially always predicting the majority "not high risk"
   class, catching only 4 of 68 genuinely high-risk claims in the test
   set. `class_weight="balanced"` reweights the *training loss*, but
   does not guarantee the predicted probabilities are well-calibrated
   around 0.5 at prediction time — a real, common gap between training-
   time class balancing and prediction-time decision thresholds. Found
   by directly inspecting the confusion matrix rather than trusting the
   accuracy number at face value.

2. **Fix: tune the decision threshold on a separate validation split.**
   Rather than hand-picking a threshold or leaving it at 0.5, the model
   now sweeps candidate thresholds (0.05 to 0.95) on a validation split
   carved out of the training data — never touching the test set during
   tuning — and picks the one maximizing F1. In initial testing (system
   Python, scikit-learn 1.8) this raised test-set F1 from 0.104 to
   0.237 and recall from 5.9% to roughly 32%.

3. **Cross-environment finding: the exact tuned threshold is not
   perfectly stable across scikit-learn versions, even at a fixed
   `random_state`.** Re-running the exact same code and seed in a
   fresh virtualenv with a newer scikit-learn (1.9 vs. 1.8 during
   initial development) picked a different threshold (0.57 vs. 0.39),
   with a correspondingly different test-set F1 outcome — because
   `RandomForestClassifier`'s internal tie-breaking during tree
   construction isn't guaranteed bit-identical across library
   versions even with the same seed. This is a genuine, disclosed
   reproducibility caveat, not a bug I "fixed" by forcing a specific
   number: the test suite (`test_tuned_threshold_is_chosen_to_maximize_validation_f1`)
   was rewritten to assert the property that's actually guaranteed —
   that the chosen threshold does maximize F1 on its validation split
   — rather than asserting a specific test-set F1 comparison that
   depends on exact floating-point tie-breaking outside this project's
   control. Both a system-Python run (scikit-learn 1.8) and a clean
   virtualenv run (scikit-learn 1.9) pass all 31 tests; the specific
   accuracy/F1/recall numbers quoted above are from one representative
   run, not guaranteed to reproduce to the decimal on every machine.

## Relationship to sibling projects

This project closes a distinct gap from the LLM/agent-focused projects
elsewhere in this portfolio (`rag-tool-agent-demo`, `ai-codegen-analyst`,
`graph-rag-ontology-demo`) — classical supervised machine learning, not
LLM-based reasoning or retrieval. It deliberately reuses the
claims-management domain shape from `ai-codegen-analyst` for narrative
coherence (both are synthetic Kfz/Personenschaden-style claims data),
but the two datasets are independently generated and serve different
purposes: `ai-codegen-analyst` demonstrates an LLM writing its own
analysis code, this project demonstrates a hand-trained, evaluated
supervised model.
